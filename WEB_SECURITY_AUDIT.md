# Web security audit

Audit date: 2026-10-14. Scope: checked-out Angular web app, Nginx config, and `directus-extensions/wellar-workspaces`. Directus global permissions, database RLS, API gateway/CORS/cookie attributes, AI Server, and the live deployment are outside the checkout and were not verifiable. This is an engineering review, not a formal compliance assessment.

## Findings

### Strengths

- Auth uses Directus session mode and `withCredentials`; the interceptor strips caller-supplied `Authorization` headers and sends credentials only to the configured API origin (`src/app/services/auth.ts:126-159`, `src/app/services/auth.interceptor.ts:8-21`). `getStoredAccessToken()` returns null (`auth.ts:335-338`). This is a stronger XSS token boundary than persisting bearer tokens in browser storage. Cookie `HttpOnly`, `Secure`, `SameSite`, domain, and lifetime settings must still be verified in Directus/proxy config outside this repo.
- Logout increments an auth generation, clears cached identity/workspace keys, and rejects stale in-flight identity updates (`auth.ts:452-479,506-559`; `company-context.service.ts:755-805`). Tests cover stale Company A data after switching to Company B.
- The workspace extension bases identity on `req.accountability.user`, rejects frontend-supplied identity/role/workspace ownership fields, checks membership and role, and uses transactions/advisory locks (`directus-extensions/wellar-workspaces/README.md`; `src/index.js:2638-2730`). The scan request loader takes the active workspace from verified membership and filters target member by workspace (`index.js:2652-2670`). The queue route applies workspace and manager-department or employee-user scoping (`index.js:2833-2871`).
- State-changing extension requests require the exact production browser Origin or an origin-less Bearer-authenticated server call (`index.js:7-14,2145-2148`). Protected file route requires authentication and checks allowed associations before delivery (`index.js:2149 onward`).
- Nginx source config sets HSTS, nosniff, frame denial, referrer and permissions policies, and CSP (`nginx.conf`). It disables index caching and gives fingerprinted build files immutable caching. Validate headers through the real TLS edge; static config alone does not prove deployment behavior.
- Angular uses standard interpolation; repository search found no `innerHTML`, `bypassSecurityTrust*`, `eval`, or document-write sinks. User-facing backend errors have safe mapping in `src/app/shared/errors/safe-error.mapper.ts`.

### Risks and evidence gaps

1. **Medium — browser storage is readable and mutable by same-origin script.** `AuthService.fetchCurrentUser()` writes email, user ID, org ID, and role metadata to localStorage (`auth.ts:384-428`); workspace context persists verified membership/context data there (`company-context.service.ts:1390-1448`). These are not credentials and server authorization must remain authoritative, but any XSS can read/alter them and stale scope can influence display or request construction. Treat all localStorage values as hints only; require fresh server-verified context for sensitive actions and clear on identity/context changes. Prefer session memory for sensitive identity metadata where practical.
2. **High verification gap — backend cookie, CSRF, CORS, and server permission policy are absent.** Login/logout/reset requests use cross-origin credentials (`auth.ts:126-205`); interceptor sends cookies to `dash.conntinuity.com`. SameSite behavior and API Origin allowlist are not evidenced for Directus. Origin checking exists only on this extension; confirm equivalent API-wide CSRF defenses for every state-changing cookie-authenticated endpoint, exact CORS allowlist, credentials policy, and cookie flags at the backend/proxy.
3. **High verification gap — tenant collection permissions/RLS cannot be proved from client code.** Client builders include tenant/department filters in several calls, but some reads such as compliance scans/results/consents are broad with limits (`operations-workflows.service.ts:508-529`). UI filters are not security boundaries. Prove Directus permissions/database RLS prevent cross-tenant reads, including guessed scan IDs, files, exports, notifications, and old workspace IDs.
4. **Medium — session refresh performs an unbounded network call.** `refreshFromCookieInternal()` posts `/auth/refresh` without an RxJS timeout (`auth.ts:618-665`), even though `/users/me` has 12s and login has 20s timeouts. A stalled refresh can keep route guards/restoration pending. Add a bounded deadline with clear recoverable error classification.
5. **Medium — route return target validation is only prefix-based in auth service.** `setPostAuthRedirect()` and `consumePostAuthRedirect()` accept any string beginning `/` (`auth.ts:266-289`). This normally prevents absolute external URLs but protocol-relative `//host` and encoded/path normalization cases deserve allowlist validation at `PostLoginRoutingService.sanitizeExplicitRedirect()` and tests.
6. **Medium — CSP allows `unsafe-inline` styles and broad HTTPS images/fonts.** Nginx CSP has `style-src 'unsafe-inline'`, `img-src ... https:`, `font-src ... https:` (`nginx.conf`). The config documents Angular runtime style injection. Narrow image/font origins and adopt nonce/hash or other supported Angular CSP strategy if feasible; keep documented compatibility reason and validate with report-only before enforcing a change.
7. **Medium — best-effort scan request webhook is not durable.** The extension commits the request/notification/activity, then makes an external webhook with 5-second timeout and only logs failure (`index.js:2732-2818,2084-2138`). A process/downstream failure can drop delivery. Use transactional outbox, bounded retry, deduplication, and dead-letter alerting.
8. **Low/Medium — debug/diagnostic logs include identifiers and raw technical context.** Production logs are often guarded, but scan-result/alert logs include scan IDs, alert IDs, member IDs, and workspace IDs (`operations-workflows.service.ts:817-867`, `compliance.service.ts:1144-1224`); Directus logs raw `error` objects at failure sites. Verify production logger redaction, retention, access control, and that provider errors cannot contain PII/secrets. Prefer server-only structured logs with hashed correlation identifiers.
9. **Low — CSP / security headers only exist in the checked-in Nginx file.** The Docker image copies the config (`Dockerfile`), but live CDN/TLS terminator, API host headers, HSTS preload/subdomains, and all error response headers were not inspected. `nginx.conf` contains nested locations that repeat headers because `add_header` changes inheritance; a regression test/synthetic check should validate every route/status.
10. **Unknown — dependency advisory state.** `package-lock.json` is committed and Docker uses `npm ci`, but no vulnerability audit or automated dependency update policy was verifiable in this pass. Do not infer dependency safety from the successful build.

## Required verification before broad rollout

- Verify cookie flags and CSRF defenses at the production API, including login, logout, refresh, workspace changes, scan request creation, and account deletion.
- Test direct API requests with a valid tenant A identity against tenant B IDs for each collection/route, including scan status/result/file/export. Confirm denial comes from the server.
- Validate deployed CSP/security headers on public HTML, hashed assets, 404s, and API errors; verify TLS redirect and cache headers.
- Run XSS/DOM injection checks on names, messages, reports, alert titles, and error content with real templates; maintain no unsafe DOM sinks.
- Check production logs and telemetry for credentials, full email/scan content, and unrestricted identifiers.
- Add security tests for session expiry during a write, concurrent context switch, CSRF rejection, origin rejection, idempotency replay, and cross-tenant lookup.

## Test evidence

Angular: 63 files / 343 tests passed. Directus extension Node proof checks: 7 passed, 2 failed because the tests invoke the extension handler with a shape that omits `router.use` or `context.services`; affected `account-deletion-request.assertions.mjs` and `workspace-create-proof.mjs`. Treat those as unverified coverage until the harness/API shape is aligned and the tests pass; no production vulnerability was inferred solely from harness errors.
